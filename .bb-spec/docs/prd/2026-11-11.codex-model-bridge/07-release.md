# 打包发布

## 用户故事

### P1：作为维护者，我想只在 GitHub 发布一个版本就自动出安装包，以便不用在本机手动打包

**用例（主路径）**
- 场景：维护者在 GitHub 创建并发布版本 `v1.3.0`。
- 操作：等待自动流程跑完。
- 预期：发布页上多出 macOS 安装包和 Windows 安装包。安装包文件名里带版本号和平台，例如 `model-bridge-1.3.0-macos.dmg`、`model-bridge-1.3.0-windows-setup.exe`。

**用例（边界 / 异常）**
- 场景：打包失败。预期：发布页上不附上残缺的安装包，自动流程显示失败。
- 场景：普通用户下载 macOS 安装包，双击打开。预期：系统提示"无法验证开发者"；用户在"系统设置 > 隐私与安全性"里点"仍要打开"后，可以正常安装和使用。项目 README 写明这个放行步骤。

## 约束

- C1 在 GitHub 上发布正式版本时，自动流程会打包 macOS 和 Windows 两个安装包，并附到这个版本的发布页上。草稿版和预发布版不触发。
- C2 安装包文件名格式是 `model-bridge-<版本号>-macos.dmg` 和 `model-bridge-<版本号>-windows-setup.exe`，版本号和发布标签一致（去掉开头的 v）。
- C3 macOS 安装包只支持 Apple 芯片、macOS 13 及以上；Windows 安装包支持 64 位 Windows 10 1809 及以上。在更低的系统版本上，安装包提示"需要 macOS 13 或更高版本"或"需要 Windows 10 或更高版本"，不安装。
- C4 安装包双击就能安装。Windows 安装时不要求管理员权限；macOS 把程序拖进"应用程序"文件夹即可。安装后第一次打开时，显示「连接到中台」设置窗口。
- C5 自动流程配置、安装包、发布说明和自动流程日志里，不出现真实 Base URL、API Key、中台品牌或其他能看出服务身份的信息。
- C6 安装包没有代码签名。README 写明 macOS 和 Windows 首次打开时怎么放行。
- C7 工具显示的版本号和发布标签一致。

## 验收

- [ ] C1：在测试仓库发布 `v0.0.1-test` 正式版 → 发布页出现两个安装包；发布一个预发布版 → 自动流程不运行。
- [ ] C2：安装包文件名和规定格式一致。
- [ ] C3：macOS 安装包在 Apple 芯片、macOS 13 的 Mac 上能运行，程序文件只包含 arm64 架构，程序声明的最低系统版本是 13.0；Windows 安装包在 64 位 Windows 10 1809 上能运行。在低于最低版本的系统上，安装时出现规定的提示。
- [ ] C4：在 Windows 普通用户账户里双击安装，全程没有管理员权限请求；两个平台安装后第一次打开，都显示「连接到中台」窗口。
- [ ] C5：在仓库、安装包解包后的全部文件和自动流程日志里，搜索测试用的 Base URL、Key 和品牌词，都搜不到。
- [ ] C6：README 里有两个平台首次打开时的放行步骤。
- [ ] C7：发布 `v1.3.0` 后，安装包里工具显示的版本号是 1.3.0。

## 验证路径

1. 在测试仓库发布一个正式版本 → 自动流程运行完成，发布页出现两个安装包，文件名符合规定。
2. 分别在 macOS 和 Windows 上下载、放行、双击安装 → 第一次打开显示设置窗口，版本号正确。
3. 解开安装包全文搜索敏感词 → 没有命中。
