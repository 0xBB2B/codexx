# 项目官网：GitHub Pages 介绍单页

## 背景与问题

想了解模型接入助手的人现在只能读仓库 README。README 偏技术：没有界面图，也没讲清"装了能得到什么"。普通用户看完很难决定装不装，也不知道装完怎么设置。外国访客则完全看不懂中文 README。

## 目标

- 访客打开一个网址，就能看懂这个工具做什么、长什么样、怎么上手、两种接入方式的区别、安全上做了什么，并找到下载入口。
- 中文和英文访客都能读：第一次打开按浏览器语言显示，访客也可以随时切换。
- 官网文件有改动并推到默认分支后自动发布；发布前自动检查，页面里出现可疑网址或 Key 时拒绝发布。

## 非目标

- 不做多页文档站：详细的安装、设置和卸载教程不单独成页。
- 不用真实截图：App 界面图用网页代码画，里面全是示例数据。
- App 界面图只画 macOS 的样子，不画 Windows。
- 不给 App 本身加英文界面：英文页里的 App 界面图保持中文。
- 不接访问统计，不引用外部字体、脚本或图片。
- 不检查中转品牌名：品牌名没法在不公开它的前提下写进检查规则，这一项靠项目约束和人工把关。

## 依赖与交付顺序

01 → 02。02 的检查对象是 01 产出的网页文件。

## 整体验证路径

1. 本地用浏览器打开官网文件，浏览器语言为中文 → 显示中文页，从上到下依次是顶栏、首屏、界面、三步上手、接入方式、安全、常见问题、下载、页脚。
2. 点「English」→ 整页换成英文，网址不变；刷新页面 → 仍是英文。
3. 把官网文件推到默认分支 → GitHub 上的发布流程自动运行，先检查后发布；打开 `https://0xbb2b.github.io/codexx/` → 看到最新页面。
4. 在官网文件里临时加一个白名单以外的网址并推送 → 发布流程在检查这一步失败，线上页面仍是上一版。

## 决策记录

- 2026-11-16 质疑结论：更便宜的做法是把 README 写好、配几张图。用户仍决定做官网，理由是官网能放下载按钮、排版更自由、能直接展示界面效果。代价是多一份要维护的内容。
- 2026-11-16 用户选择中英双语切换。否决「只用中文」和「只用英文」：用户希望外国访客也能看懂；只用英文又和 App 的语言对不上。
- 2026-11-16 用户选择单页。否决「单页 + 使用文档页」：内容控制在 README 的范围内，好维护。
- 2026-11-16 用户选择用网页代码画 App 界面。否决真实截图：截图很容易带出真实 Base URL，每次发版还要重新截图、人工检查。
- 2026-11-16 用户先看了三版风格（A 清爽原生、B 深色极客、C 纸本编辑），选了 A。A 和 App 用同一套颜色，用户从官网到 App 不会觉得换了一个产品。官网新增的字号、间距和组件写进 DESIGN.md 第 11 节「官网」，颜色、圆角、阴影全部沿用 App 的规范。
- 2026-11-16 用户确认：英文页里的 App 界面图保持中文，并注明"App 界面只有中文"，免得让人以为 App 有英文版；英文页里「中台」统一叫 relay，和示例地址 relay.example.com 一致；页脚保留"与 ChatGPT、Codex 的所有者没有隶属关系"的声明。
- 2026-11-16 用户选择用 GitHub Actions 发布。否决「docs/ 目录直接发布」：Actions 能在发布前加检查。
- 2026-11-16 用户选择：第一次打开按浏览器语言选，切换后记住；中英文共用一个网址、在页内切换。否决「中英文各用一个网址」：只维护一个文件。代价是分享出去的链接显示哪种语言，取决于对方的浏览器。
- 2026-11-16 用户选择：默认分支上的官网文件有改动时自动发布，也能手动触发。否决「只手动触发」（容易忘）和「发正式版时发布」（只改官网文字也得等发版）。
- 2026-11-16 用户选择发布前做网址白名单检查，不通过就不发布。规则只列允许出现的网址，不列真实地址，否则检查规则本身就会把真实地址公开出去。
- 2026-11-16 用户选择：发布前检查只防"误写"，不防"故意绕过"。检查是为了拦住维护者不小心写进去的真实地址；能故意构造网址骗过检查的人必须有默认分支的推送权限，而他同样能直接改掉检查程序，所以检查挡不住他。审查列出的几种故意构造写法记录在案、不再加规则：中文标点后接中文再接域名、路径结尾 `/..`、网址中间夹制表符或换行、`https:\` 反斜杠写法。否决"也防故意绕过"：这类写法能一直造下去，规则会越来越复杂、越来越容易误伤正常文字。
- 2026-11-16 用户选择：窗口宽 356px 及以下，App 界面图再缩一档到 46%。原因：52% 后图宽约 322px，320px 宽的手机内容区只有 288px，图左右各被裁约 17px，时钟被截断。门槛原定 340px，看预览时发现 341～354px 仍会裁边，用户改选 356px。否决「保持裁边、只在 DESIGN.md 写明」：会裁到图里的文字。
- 2026-11-16 用户选择：窄屏下页签文字不折行，放不下时整个页签换行；600px 及以下页签内边距 12px；英文页签改成短文案 Setup / Main window / Menu bar（方案 B），让 320px 宽的英文页也能排一行。否决方案 A「保留 First-run setup / Main window / Menu bar menu、约 415px 以下排成两行」：用户更看重英文手机上排一行。
- 2026-11-17 用户要求官网下载不再跳转 Releases 页面、每次下载最新正式版、页面写清版本号（原话：「我希望主页里的下载能够直接下载最新版本的不需要再跳转一次GitHub 的 Releases 页面 并且每次下载的都是最新发版的版本，并且页面上也清楚版本号」），并要求「下载放在最上面，一开始就让用户能够看见点击下载」。选了做法 A：发布官网时把最新正式版的版本号和两个安装包直链写进页面；每次发正式版后自动重新发布官网，发预发布版不动。否掉了做法 B「访客打开页面时再去问 GitHub 接口」（每个访客每小时最多 60 次，接口失败就看不到版本号，还多一个对外请求）。下方「下载」区保留，放系统要求、放行步骤和「查看所有版本」；还没发过正式版时首屏只放一个禁用的「暂未发布」。推到默认分支时照常发布官网的规则不变。
- 2026-11-18 01 官网页面的文字跟上 multi-relay 需求（2026-11-16.multi-relay）已经改过的页面，页面本身没有变化。multi-relay 把「中台」改称「中转」，并把主窗口改成「转发总览 + 中转配置 + 底部状态栏」，官网页面当时已按它改好，这份 PRD 的文字却还是旧的。这次改的是：C3 首屏说明、C6 第 2、3 步、C7 流程图和两张卡片、C8 第二张卡片、C9 第 1、2 条、C13 里的「中台」都换成「中转」；C5 三张界面图换成页面上的写法：首次设置多了「名字」一栏，标题是「连接中转服务」；主窗口是转发总览、两行配置的「中转配置」卡片和新的底部状态栏，没有「中台连接」「运行状态」卡片；菜单项是「使用中转」。C7 模型列表示意补上「官方模型」「中转模型」两个分组标题和「A家 · auto」。
